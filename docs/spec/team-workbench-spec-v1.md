# AI 시대 팀 워크벤치 (가칭) — 통합 스펙 v1

> 사람과 점점 자율화되는 시스템 사이의 **의도·제약·책임 층**.
> 사람은 하네스를 소유하고, 그 안에서 AI가 자율적으로 개발해도 이해와 책임이 유지되게 한다.
>
> v0([[team-workbench-spec-v0]])의 네 면·루프·배치는 유지하되, 근간을 코드 변경에서 지속 객체(의도·제약·책임)로 옮기고, 자율 수준·서명된 책임 원장·사람/AI 이중 표면을 추가한다. v0의 구현 순서는 거의 그대로다.

## 0. 근간

지속되는 객체는 셋뿐이다. 코드·인프라·문서·실행 환경은 이 셋의 **실현체(realization)**이며 교체·재생성 가능하다.

| 객체 | 내용 | 1급 ID |
|---|---|---|
| **의도 Intent** | 무엇을 원하는가, 무엇이 "더 낫다"인가 | 있음 |
| **제약 Constraint** | 계약·불변식·규칙·예산·자율 수준 = 하네스 = 시스템의 정체성 | 있음 |
| **책임 Accountability** | 누가 무엇을 판단했고 결과가 어땠나 (판단·결정·결과) | 있음 |
| 실현체 | 코드·문서·인프라·런타임 | 없음 — 지속 객체에 닻으로 연결될 뿐 |

설계 원칙: 코드가 전부 재생성돼도 제약과 책임 기록은 같은 ID를 유지한다.

## 1. 확정 결정 (v0에서 바뀐 것은 ★)

| 항목 | 결정 |
|---|---|
| 단위 | 변경(Change) = **하네스 또는 실현체의 변화** ★ (코드 diff에 한정하지 않음) |
| 구조 | 네 면 — Context / Watch / Change / Work. 본체는 Change·Context, Watch·Work는 실현체 쪽 |
| 사람의 역할 | 하네스(=**차터 Charter**, 대외 용어)의 **설계자·소유자** ★. 변경마다의 판단자가 아님. 개입률 하락 = 성숙. 용어 주: 에이전트 진영(OpenClaw 등)에서 'harness'는 에이전트 런타임 골격을 뜻하므로 대외적으로는 Charter를 쓴다 |
| 하네스 생성 | 작성하지 않는다. 판단에서 컴파일된다(승격). 승격 규칙은 원천 판단과 사람이 읽을 한 문단을 반드시 가진다 ★ |
| 자율 수준 | 범위·제약별 L0~L3 ★. 승격은 결과 채점 이력, 강등은 회귀 1회 자동 |
| 범위 규칙 | **제약은 넓은 범위 우선(상위가 하위를 구속) / 컨텍스트·설정은 좁은 범위 우선(하위가 상위를 구체화)** ★ |
| 범위 구조 | 트리가 아니라 **제품 × 팀 격자 + 소유 지도(Ownership)** ★. 제품=공유 하네스(헌법), 팀=관심사·스타일·팀 제약. 소유 지도는 CODEOWNERS 가져오기로 시작. 격자는 해석 엔진 안에, UI는 "제품 헌법 / 우리 팀 / 내 것" 세 층으로 |
| 책임 원장 | **투명성 로그**(머클 트리 + 서명 체크포인트 + 포함/일관성 증명) ★. 증인·TSA 타임스탬프는 플러그인, 블록체인은 체크포인트 앵커링 옵션. 데이터는 외부로 나가지 않음 |
| AI 의존 | AI는 가속기이지 기반이 아님 ★. AI 개입 단계마다 결정론적 폴백, 호출은 교체 가능한 프로바이더(BYOK·로컬 모델) 경유 |
| 감사 산출물 | 감사 패키지(기간 T의 유효 제약·Change·판단·자율 수준·예외 + 포함 증명) ★ |
| 행위자 | 사람과 **에이전트 인스턴스** 모두 키를 가진 1급 행위자 ★. 권한 = 행위자 종류 × 자율 수준 |
| 표면 | 사람=UI, AI=MCP/API. 같은 이벤트 로그. 제품 자체가 **API-first** ★ |
| 승인 브로커 | 승인은 이제 에이전트의 기본 기능(OpenClaw·Grok Bot). 우리는 승인을 만들지 않고 **승인의 기록 주체**가 된다 — 에이전트가 `/gates`에 묻고, 사람은 자기 도구·채팅에서 답하고, 우리는 판단을 원장에 기록하고 자율 수준을 적용 ★. 이를 위해 서버 API(원격)는 v0 범위로 앞당김 |
| 에이전트 | 만들지 않는다. Work는 기존 에이전트에 넘기고 결과를 회수 |
| 개인/팀 | 세션은 개인, PR은 팀. 개인 층 불침범. 개인 판단 지문은 본인만 사용 |
| 배치 | 로컬 데몬(+로컬 MCP) + 원격 팀 서버. 원격 MCP는 v1 이후 |
| 원천 | **원장이 유일한 원천** ★. 리포의 md·CLAUDE.md는 렌더 결과이자 가져오기 소스. 언제든 완전 내보내기(md 렌더러) + 형식 공개 + 셀프호스트로 종속 우려를 해소 |
| 지식 구조 | 고정 온톨로지 — 타입 8(Intent·Constraint·Decision·Concept·Anchor·Scope·Actor·Change), 관계 6(anchors·supersedes·conflicts·references·derived_from·scoped_by) + `Concept`(OKF)·라벨 있는 `relates_to`. **운영 온톨로지 원칙: 동작을 바꾸지 않는 온톨로지 요소는 만들 수 없다.** 확장(새 범위 축·제약 종류·관계 종류)은 v2 플러그인으로 — 검사기·영향 의미·라우팅 효과를 코드로 함께 등록해야 함. 모델링 UI는 비목표. 대외 서사에 '온톨로지'를 앞세우지 않음 ★ |
| GHA 의존 | 영향 계산·검증은 데몬이 로컬(post-commit/pre-push)에서. GitHub Action은 데몬 없는 기여자·CI 게이트 폴백. 서버 클론 계산 없음 ★ |
| 판단 권한 | 행위자 종류 × 자율 수준 × **범위별 판단 종류(하네스/실현체)** — 비개발자는 하네스 Change 판단자, 개발자는 실현체 판단자 ★ |
| 낡음 판정 | 닻 해시 3층 + review/stale 2단계 + 커밋 묶음. 시그니처 변경은 무조건 stale |
| 첫 사용자 | AI 세션을 매일 여는 개인 개발자(터미널) → PR에서 팀. 사업 2축은 "감사 가능한 하네스"(규제 조직) ★. 비기술 창업가는 v2(터미널 없는 경로, §13.4) |
| 첫 가치 | PR 리뷰가 아니라 **에이전트 루프 안에서 하네스가 작동하는 순간**(편집 전 훅이 제약을 에이전트에게 돌려줌) ★ |
| Change 도출 | 세션도 턴도 아님. 경계=커밋(솔로)/PR(팀), 내부 군집=닻 근접. 제약에 닿지 않는 Change는 판단 없이 settle("하네스 밖" 상태) ★ |
| 판단 추출 | 세션 내 판단은 대화에서 추출(방향 수정 발화·되돌리기·실패 후 재지시). 재현율 낮아도 됨 — 같은 닻 3회 규칙이 흡수 ★ |
| 표면 우선 | 터미널 우선(CLI/TUI, 개입은 에이전트 출력 안에). 웹 UI는 팀 서버·비기술 소유자용 ★ |
| 지표 | 사용자·확산 > 결제. 핵심 명제: 판단 축적 후 제안 수용률↑·회귀율↓. 성숙: 자동 판정 비율·예외율·개입당 변경 수 ★ |
| 중립 | 벤더·도구·모델 중립과 형식 공개는 기능이 아니라 생존 조건 ★ |
| 언어 | Go(데몬·서버), React(UI), TS·Python(어댑터·SDK) |

비목표(v0): 에이전트 런타임, 자체 실행 런타임, 코드 입력 표면(IDE) 경쟁, 원문 컴파일, 원격 MCP, 사람별 판단 채점, 자동 머지, 일반 사용자 대상(사용자화 세계의 확장은 비전에만), **ZK 증명**(본문/메타 분리 해시 구조만 준비), 데이터의 체인 저장.

## 2. 네 면과 루프

바운디드 컨텍스트(코드 패키지 경계와 1:1):
| 컨텍스트 | 객체 | 분류 |
|---|---|---|
| **Harness** | Intent · Constraint · Scope(자율 수준·상한) | 코어 |
| **Accountability** | Change · Judgment · Outcome · 원장(소유) | 코어 |
| **Realization** | Anchor · Finding(Watch) | 지원 |
| **Supply** | Context 합성 · 어댑터 · MCP | 일반/어댑터 |
| **Work** | 작업 배분 | 일반/어댑터 |
원장은 Accountability만 append하고 나머지는 커맨드를 통해 발행한다.


| 면 | 역할 | 무게 |
|---|---|---|
| **Context** | 개인·팀·제품 층의 제약·설정·규칙·스킬·결정을 유지·합성해 사람과 AI에 공급 | 본체 |
| **Change** | 의도 → 제안 → 판단 → 배포 → 결과. 판단에서 제약이 파생·승격 | 본체 |
| **Watch** | 실현체를 제약에 대해 감시. finding(어디·무엇·왜) | 실현체 |
| **Work** | finding·의도를 작업으로 만들어 사람/에이전트에 배분, 결과를 Change로 회수 | 실현체 |

루프: Watch → finding → Work(+Context) → 제안 → Change(판단: 사람 또는 하네스) → 배포 → Watch(결과) → Context(제약 축적) → 자율 수준 조정.
사람은 **의도 선언·판단·승격 승인·자율 수준 조정·예외** 다섯 지점에만 있고, 성숙할수록 앞의 둘은 줄고 뒤의 셋만 남는다.

## 3. 데이터 모델

### 3.1 지속 객체
```
Intent      {id, text, source: human|issue|inferred, scope, by, at}
Constraint  {id, kind: contract|invariant|rule|budget|autonomy, scope, body, checkable?: spec,
             origin: judgments[] (승격 원천) | authored, explanation (사람이 읽는 한 문단),
             state: generated|verified|review|stale|retired, supersedes?}
Judgment    {id, change_ref, decision: accept|modify|reject, reason, by(actor), at, source: session|review|harness, sig}
Decision    {id, kind: adr, from: judgments[], body(MADR), supersedes?, anchors→realizations}
Outcome     {id, change_ref, window, signals[], verdict: confirmed|regressed|unknown}
```
- `Constraint.scope` 해석: 넓은 범위 우선. `Context` 문서(guide·concept·설정·스킬)는 좁은 범위 우선(§4).
- `autonomy` 종류의 Constraint = 특정 범위·닻에 대한 자율 수준 선언(§4.2).

### 3.2 실현체 닻 (Realization Anchor)
```
code://<path>#<symbol>   route://<METHOD> <path>   ui://<Component>
schema://<Type>          infra://<tool>:<resource>  doc://<doc_id>
contract://<group>/<key> (후속 런타임)
```
- 관계 방향: **지속 객체 → 닻**(제약이 실현체를 가리킨다). 닻이 사라져도 객체는 남고 `unrealized` 표시.
- 해시 3층 signature/body/file. 해석기 v0: TS/JS, Python, Go, React, generic. `AnchorMoved`로 이동 추적.

### 3.3 Change (일반화)
```
Change
  id, kind: realization|harness   -- 코드/인프라/문서 변경 | 제약·자율 수준·결정 변경
  mode: manual | session | delegated | autonomous
  intent_ref (또는 "의도 없음" 명시)
  sessions[] (§3.4), proposals[] {diff_ref|constraint_diff, actor, at, sig}
  impact {constraints[]{ref, relation: references|violates|conflicts}, decisions[], anchors[], graph}
  judgments[] (§3.1), verification, deployment
  outcome_ref, derived[] (승격된 Constraint/Decision)
  autonomy_applied: L0..L3   -- 이 변경이 어느 수준에서 처리됐는가
  state: proposed → judged → deployed → observed → settled
```
- 하네스 변경(`kind: harness`)은 항상 L0(사람 판단). 자율 수준 상향은 하네스 변경이다.
- AI 컨텍스트 입력 = settled Change의 `derived` + verified Constraint + 닻 이력.

### 3.4 Session (개인 층, 로컬)
v0 §3.3과 동일: tool, actors, intent, touched, judgments[], summary(원문 미포함). 캡처 우선순위: 훅 → MCP 도구 → 커밋 트레일러 → PR 추론. 공유는 PR 시점 사용자 선택(기본: 의도+요약).

### 3.5 Finding / Work
v0 §3.5·3.6과 동일. Finding kind v0: `doc-stale`, `constraint-violation`, `decision-conflict`, `ai-unreviewed`, `regression`, `no-test`. v1: `unowned`, `cross-team`. Work의 context_bundle = 범위의 제약·결정·스킬 + 닻 이력. 에이전트는 실행하지 않고 넘긴다.

### 3.6 행위자와 서명
```
Actor {id, kind: human|agent, identity: oidc|keypair, agent?: {tool, model, instance, owner(human)}}
```
- 모든 이벤트에 `actor` + 서명. 에이전트 인스턴스는 자기 키로 서명하고 `owner`(책임지는 사람)를 가진다.
- 권한 = 행위자 종류 × 해당 범위의 자율 수준. 에이전트는 L0 범위에서 제안만, L2 이상에서 settle까지.

### 3.6 Discussion · 그래프 · 렌더/가져오기
- `Discussion {id, subject: Constraint|Decision|Change|Concept, comments[] {actor, body, at, sig}}` — 원장 이벤트 `Commented`. `Judgment.reason`이 스레드를 참조할 수 있다. git이 아니라 원장에 산다.
- **지식 그래프 = 원장의 투영**(엣지 테이블 + 재귀 CTE, 그래프 DB 없음). MCP 질의: `related(id)`, `path(a,b)`, `why(constraint)`, `what_touches(anchor)`, `search`. AI는 md 파일이 아니라 정형 객체와 관계를 읽는다.
- **렌더러**: 원장 → md(ADR 파일·CLAUDE.md managed 블록·.cursor/rules·llms.txt) · MCP 리소스 · 웹. md 렌더러가 곧 완전 내보내기.
- **가져오기**: 리포 md(이관), 에디터에서 직접 고친 md(데몬 파일 감시 → 제안 커맨드), 웹 편집 — 세 경로 모두 같은 커맨드로 원장에 들어간다. 충돌 시 원장이 이기고 사용자에게 diff. 왕복 지연 목표 수 초.

### 3.6a 승인 브로커 (Gate as API)
```
POST /gates {actor(agent), scope, anchors|action, proposal_ref, requested_level}
 → 즉시 {decision: allow|deny|ask, gate_id, policy_ref}   -- 자율 수준·상한·소유 지도로 결정
 → ask인 경우 사람이 자기 채널(도구·채팅·웹)에서 답 → POST /gates/{id}/resolve {decision, reason, by, sig}
```
- 에이전트의 자체 승인 UI를 대체하지 않는다. 우리는 판정 정책과 기록이다. `Judged` 이벤트로 남고 승격 원료가 된다.
- 행동(action)도 실현체 변화의 한 종류로 취급할 여지를 둔다(자격증명을 쥔 상시 에이전트의 폭발 반경). v0는 코드 실현체만.

### 3.6b 쓰기 모델 (커맨드·애그리게이트)
CQRS의 쓰기 측을 명시한다. 이벤트는 커맨드 핸들러의 결과로만 생기며, 규칙은 애그리게이트에서 집행된다.
| 애그리게이트 | 커맨드(예) | 집행 규칙 |
|---|---|---|
| `Change` | open, addProposal, judge, deploy, recordOutcome, settle | 하네스 변경은 L0 판단 필수 / 영향 없는 Change는 판단 없이 settle / settle은 outcome 또는 창 만료 후 |
| `Constraint` | draft, verify, promote, demote, supersede, retire | 승격은 원천 판단+설명 문단 필수 / 하위 범위는 상위보다 엄격하게만 / 재승격은 이력 재축적 |
| `Scope` | setAutonomy, setCap | 상한 초과 불가 / 상향은 하네스 Change 경유 |
| `Gate` | request, resolve, expire | 정책 판정(allow/deny/ask) / resolve는 해당 범위 판단자만 / 만료 정책 |
| `Session` (개인·로컬) | start, recordTurn, end, share | 원문 저장 금지 / share는 사용자 선택분만 |

### 3.6c 일관성 모델 (연합 로그)
개인 원장(로컬)과 서버 원장은 연합된 append-only 로그다. **서버 seq가 유일한 전역 순서**이며, 데몬이 올리는 이벤트는 *제안*이고 서버 append 시점에 애그리게이트 규칙으로 재검증되어 *확정*된다. 거부는 `Rejected{reason}` 이벤트로 기록된다(예: 오프라인에서 낡은 제약을 기준으로 내린 판단, 동시 승격 충돌). 데몬은 거부를 받아 로컬 투영을 정정한다. 충돌은 사라지지 않고 기록으로 남는다.

### 3.7 이벤트 로그 = 책임 원장 (투명성 로그)

소명 대상과 수단:

| 소명 | 수단 |
|---|---|
| 무결성(기록 불변) | 머클 트리 위 append-only |
| 진정성(그 행위자가 했다) | 서명 — 사람 OIDC 키리스 서명, 에이전트 인스턴스 키 |
| 존재 시점 | 서명 체크포인트 + 외부 타임스탬프(TSA, RFC 3161) 플러그인 |
| **완전성(빠진 것 없음)** | 포함 증명 + 체크포인트 간 일관성 증명 (해시 체인만으로는 불충분) |
| 절차 준수(하네스 적용) | 이벤트에 당시 유효 제약·자율 수준 스냅샷 해시 포함 |
| AI 출처 | 요청/응답 해시 + 시각. 벤더 서명 영수증이 있으면 첨부. 부인 방지는 업계 한계로 명시 |

- 구조: CT/Sigstore(Rekor) 계열. 주기적 체크포인트에 서버 서명, 옵션으로 외부 증인(witness) 공동 서명.
- 이벤트는 `meta`(행위자·시각·타입·참조·본문 해시)와 `body`로 분리 해시 → 본문을 빼도 증명 성립. **선택적 공개**(편집본 + 포함 증명)가 ZK를 대체. ZK는 비목표.
- 블록체인: 체크포인트 해시 앵커링 플러그인만. 다자간 합의 불가 환경 전용. 데이터는 올리지 않음.
- 타입(v0 §3.7) + `AutonomyChanged`, `ConstraintPromoted`, `ConstraintDemoted`, `ExceptionRaised`, `Checkpoint`.
- 키 관리: 에이전트 키는 `owner` 아래 발급·회전·폐기. KMS/HSM 연동은 v1 이후.

### 3.8 감사 패키지
`audit export --from T1 --to T2 --scope <범위>` → 유효 제약(시점별), Change·판단·자율 수준·예외 목록, 각 이벤트의 포함 증명, 체크포인트·타임스탬프, AI 출처 한계 명시. 감사인이 우리 서버를 믿지 않고 검증 가능해야 한다.

## 4. 범위와 자율

### 4.1 범위 격자와 소유
```
Scope   = org × product × team × (repo, path glob) × person   -- product와 team은 직교 축
Ownership {scope, anchors: globs | contracts[], judges: actors[]}   -- CODEOWNERS 가져오기로 초기화
```
- **제약**: 상위가 하위를 구속. 제품 제약은 모든 팀을, 팀 제약은 그 팀 소유 실현체를. 하위는 더 엄격하게만. 충돌 시 상위 승리 + finding.
- **컨텍스트·설정·스킬**: 하위가 상위를 구체화. 팀별 규칙 파일 렌더는 다르되 제품 블록은 동일. 한 리포를 여러 팀이 쓰면 경로 glob으로 분할.
- **판단 라우팅**: 변경이 닿은 제약·닻의 소유 범위 판단자가 필요. 타 팀 소유 닻을 건드리면 그 팀 판단자 없이 settle 불가(`Change` 애그리게이트 규칙). 편집 전 훅이 "이 닻은 b팀 소유, 제약 X"를 주입.
- **팀 간 충돌**: 다른 팀 제약이 같은 닻에 상충 → `decision-conflict`가 제품 범위 인박스로 → Discussion → 제품 제약 승격 또는 소유 경계 정리(컨텍스트 매핑을 운영 중에 수행).
- **미소유**: 소유 지도 빈칸은 `unowned` finding, 해당 변경은 제품 범위 판단자에게. 소유 지도 변경은 하네스 Change(L0).
- 개인 층: 팀이 읽지 않고, 위로 올라가지 않으며, 팀·제품 제약을 완화할 수 없다.
- 온톨로지 확장(범위 축 추가 등)은 v2 플러그인, 행동 효과 필수(§1).

### 4.2 자율 수준 (Constraint kind=autonomy)
| 수준 | 판단 | 에이전트 권한 |
|---|---|---|
| L0 | 사람이 전부 | 제안만 |
| L1 | 하네스가 판정, 사람 확인 후 settle | 제안 + 판정 초안 |
| L2 | 하네스가 settle, 사람은 표본 검토 | settle (표본 대상) |
| L3 | 하네스가 settle, 예외만 사람 | settle |
- 기본 L0. 승격 조건: 해당 범위의 결과 채점 이력(예: 최근 N건 회귀 0, 하네스 판정과 사람 판단 일치율 ≥ 임계). 승격은 하네스 변경 = 사람 승인.
- 강등: 회귀 1회 → 한 단계 자동 강등 + `ExceptionRaised`. 재승격은 이력 재축적 필요(즉시 복귀 불가). 규제 범위는 상한 고정(예: L1 초과 금지)을 제약으로 선언. 비기술 소유자 보호용 제품 층 기본 상한(L1) 제공.
- L2 표본 검토는 무작위가 아니라 영향 그래프 반경이 큰 변경 우선.
- 사람 개입률·자동 판정 비율·예외율을 범위별로 기록(§10).

## 5. 배치와 표면

v0 §4와 동일: 팀원 각자 로컬 데몬(개인 층·세션 캡처·닻 해석·verify·로컬 MCP·파일 실체화) + 원격 팀 서버(이벤트 원장·투영·팀/제품 층·GitHub App·웹훅·UI). 도구는 로컬만 안다. 서버 없는 기간 허용. 헤드리스 데몬(CI·클라우드 에이전트용)은 v0에 포함, 원격 MCP/API는 v1 첫 항목(클라우드 에이전트·터미널 없는 경로·IDE 없는 팀원). 지식 객체의 원천은 원장이며 리포 md는 렌더/가져오기 경로.

이중 표면(★):
- **AI 표면**: MCP(로컬) + HTTP API(서버). 읽기: 컨텍스트 묶음, 제약, 닻 이력, 자율 수준. 쓰기: 의도 등록, 제안, 판단 초안, finding, 세션 사실. 모든 쓰기는 에이전트 서명.
- **사람 표면**: UI. 의도 선언, 판단, 승격 승인, 자율 수준 조정, 예외 처리.
- 제품 API는 OpenAPI로 먼저 정의하고(design-first) 데몬·서버·UI가 그 구현체다.
- **AI 폴백 규칙**: 판단 이유 초안·결정 취지 대조·review/stale 분류·세션 요약·승격 제안은 AI 가속 단계이며, 각각 결정론적 폴백(사람 직접 입력 / 전부 stale 보수 분류 / 제목만 요약 / 빈도 기반 제안)을 가진다. AI 호출은 프로바이더 인터페이스 경유(BYOK·로컬 모델·벤더 교체 가능).

## 6. 면별 상세 (요지)
- **Context(Supply)**: 원장 → 렌더러(md·MCP·웹), 가져오기(리포 md·파일 감시·웹 편집). 어댑터(Claude Code·Cursor 먼저), 실체화(포인터 분리·managed 블록·파일 단위), 사이드카 manifest, 렌더 조건 `verified|review && audience∋ai`. `concept`는 OKF. 상세는 [[knowledge-layer-spec-v0]].
- **Change**: 영향 계산은 **코드가 있는 곳에서** — 데몬이 post-commit/pre-push에서 수행해 서명 결과를 서버에 올린다. GitHub Action(헤드리스 데몬)은 데몬 없는 기여자·CI 게이트 폴백. 서버 클론 계산은 없다. 도출 규칙 — 경계는 커밋(솔로)/PR(팀), 내부 군집은 닻 근접성. 한 과업 의도(`/goal`)에 Change N개가 매달림. 영향 계산(diff→닻→제약·결정·그래프 반경2). **이유 입력은 영향 있는 판단에만**(제약·결정·불변식에 닿지 않으면 판단 없이 settle). 판단 이유 AI 초안→"수정 없이 확인" 한 번. 결과 귀속 v0는 보수적(되돌림·같은 닻 핫픽스·창 내 오류율 급등). 리뷰 화면에 세션 판단 표시. 영향은 같은 객체를 두 렌더러(기술/평문)로. 하네스 변경도 같은 흐름.
- **세션 판단 추출**: 턴을 `accept/redirect/revert`로 분류(폴백=규칙: 되돌리기·부정어 패턴·실패 후 재지시 / 옵션=로컬·BYOK 모델). `redirect/revert`만 판단 후보로 개인 층에. 훅 없는 도구는 git 신호(커밋·reflog·diff)로 Change 도출과 사후 영향까지 지원(루프 내 개입만 불가).
- **Watch**: 원천 v0 = **세션 훅(실시간, 1순위)**·git diff·해석기·CI·배포 웹훅·오류율 웹훅. 편집 전 훅에서 닻이 제약·결정에 묶여 있으면 에이전트에게 컨텍스트로 돌려준다(L0=경고·주입, 차단은 자율 제약이 명시할 때만). PR 영향 코멘트는 이것의 사후 요약. 자체 런타임은 후속 원천.
- **Work**: `work dispatch` 명령 → 컨텍스트 묶음과 함께 에이전트 세션 시작 → 결과 Change.

## 8. 프라이버시·책임
- 개인 층 불침범. 세션 원문은 머신을 떠나지 않는다. 첫 화면에 "머신을 떠나는 데이터: 없음(서버 미연결)" 명시, 세션 요약은 사용자가 열어 볼 수 있는 파일.
- 세션 공유 기본값은 팀 정책으로 설정 가능하되 개인은 항상 축소할 수 있다(확대 강제 불가).
- 판단 채점은 모델별·닻별·범위별. **사람별 집계 없음**. 개인 판단 지문(축적된 개인 제약·취향)은 본인 데몬에서만 개인 하네스로 사용.
- 형식 공개: Intent·Constraint·Judgment·Decision·Outcome·Change·Session·Finding의 JSON Schema. 구현·호스팅·앵커링이 유료 후보.
- 출처 지문: 모든 산출물에 행위자·모델·프롬프트·원천 판단·해시·서명. AI 생성물 표시 의무 등 규제의 증빙.
- 선택적 공개: 감사인·고객에게 편집본(본문 해시만) + 포함 증명으로 공개 범위를 제한. 코드·프롬프트를 내보내지 않고 절차 준수를 증명.

## 9. 첫 절단 (v0 구현)

순서(시나리오 §13로 조정 — 루프 내 개입이 GitHub App보다 앞):
1. **데몬**: 닻 해석기(TS·Python·generic) + Context 개인 층 + Claude Code·Cursor 어댑터 + **편집 전 훅 → 제약/결정 컨텍스트 주입** + 세션 캡처(훅·MCP 도구·커밋 트레일러·reflog 폴백) + 판단 추출(규칙 폴백) + 로컬 MCP + `verify` + CLI/TUI 인박스·닻 이력. 서버 없이 동작. 헤드리스 모드 포함.
2. **서버**: 이벤트 원장(머클·체크포인트·meta/body 분리) + sync + **승인 브로커 API(`/gates`)** + GitHub App(PR → Change: 영향·판단 초안·이유 확인, 세션 공유 선택) + 배포 웹훅(결과 창) + 웹 인박스·미리보기·닻 이력.
3. **Watch v0**: `doc-stale` · `ai-unreviewed` · `decision-conflict`. 이후 `regression`·`no-test`·`constraint-violation`.
4. **Work v0**: `work dispatch` — finding/의도 + 컨텍스트 묶음 → 에이전트 세션 → 결과 Change.
5. 승격(같은 닻 3회 → 제약, 거부 → 규칙), 설명 문단·원천 판단 링크 필수.
6. 어댑터 확장, Go·React 닻, 지식 그래프·하네스 뷰, 제품 층.
7. (v1) 원격 MCP → **웹 편집·Discussion·범위별 판단 권한(팀 B 경로, §13.8)** → 클라우드 에이전트 경로 → 터미널 없는 경로(§13.4) → 배포 프로바이더 닻 → 투영 스냅샷 → 감사 패키지·TSA.
8. (후속) 자체 런타임 합류, 계약 지도.

v1 추가분(비용 낮고 나중에 못 바꾸는 것만): 지속 객체 독립 ID와 객체→닻 관계 방향 / `Change.kind: harness` / `autonomy` 제약(기본 L0) / 원장 머클·meta/body 구조 / 승격 시 원천 판단 링크·설명 문단 / OpenAPI 우선 정의 / 영향 객체의 이중 렌더러(기술·평문).
핵심 명제 실험: 우리 리포에서 3개월.

## 11. 비전·가정·시나리오

### 11.1 결과물
하네스 소유자의 작업대(사람 표면) + 책임 원장(서명된 이벤트 로그) + 컨텍스트 공급기(AI 표면)가 한 몸. 시간이 갈수록 첫째는 얇아지고 둘째·셋째가 두꺼워진다.
- 6개월: "에이전트가 우리 규칙을 어기기 전에 알아서 멈춘다." (PR을 겁 없이 머지하는 것은 그 결과)
- 18개월: 판단 채점·닻 이력이 기본 컨텍스트. Work 루프가 판단 외 무개입으로 돈다. 제품 층·L1~L2 범위 등장.
- 3년: 자체 런타임 합류, 계약 지도. 조직 자산이 "결정과 제약의 저장소"로. 사람은 하네스만 본다.

### 11.2 가정과 반증
| 가정 | 반증 |
|---|---|
| AI 변경에는 사람의 판단 또는 사람이 소유한 하네스가 필요하다 | 하네스 없는 자동 머지가 일반화되고 문제가 없다 |
| 판단은 캡처 가능하고 축적되면 AI 오류가 준다 | 3개월 후 수용률·회귀율 불변 |
| 제약·결정은 코드에서 도출 불가라 남는다 | 모델이 코드만으로 팀 규칙을 재구성 |
| 결과를 변경에 귀속시킬 수 있다 | 귀속 정확도 낮음 |
| 책임 구조는 기술보다 느리게 바뀐다 | 에이전트에 법적 책임 귀속이 일반화 |

### 11.3 시나리오별 유효성
- 점진·불균등 발전(가장 가능성 높음): 자율이 커질수록 하네스가 결과를 좌우 → 더 중요.
- 강력하지만 도구적 AGI: 책임·제약 층으로 남음. 사람은 변경을 안 보고 하네스만 본다.
- 코드의 소멸(사용자마다 재생성): Change·Finding의 코드 전제는 무너지나 지속 객체(§0)는 남음. 제품 층 제약 = 헌법, 개인 층 = 개인 조례. 이때 대상이 IT 팀을 넘어 확장될 수 있음(비전에만).
- 규제·윤리의 제동: 감사 가능성·인간 감독 의무가 이 제품의 두 번째 수요 축.

### 11.4 차별점 (기존 패러다임 대비)
단위가 의도·제약·책임(코드·인프라 아님) / 하네스는 작성이 아니라 컴파일 / 자율 범위를 사람이 소유(AI가 사람을 돕는 방향의 반대) / 개인 층 불침범 / 런타임·벤더·도구 중립.

### 11.5 인접 제품과의 관계 (OpenKB · OpenClaw · Grok Bot)
| | OpenKB | OpenClaw | Grok Bot | 우리 |
|---|---|---|---|---|
| 정체 | 문서→위키 컴파일 | 개인 에이전트 런타임(로컬, 채팅 채널) | 상시 클라우드 에이전트(벤더, Cursor 번들) | 의도·제약·책임 층 |
| md | 산출물 | SOUL.md·AGENTS.md = 정체성·규칙 | 벤더 설정 | 가져오기 소스·렌더 대상 |
| 승인 | — | 원격 액션 승인 | 필요 시 복귀 | 승인 브로커 + 원장 기록 + 제약 컴파일 |
| 자율 | — | 사용자 설정 | 벤더 정책 | 범위별 L0~L3, 결과 채점 |
| 책임 기록 | — | 세션 로그 | 벤더 내 감사 로그 | 서명·머클 원장, 벤더 밖, 감사 패키지 |
| 코드 결합 | — | — | Cursor 경유 | 닻·제약·영향 |
관계: OpenKB는 가져오기 어댑터. OpenClaw·Grok Bot은 Work의 dispatch 대상이자 승인 브로커의 클라이언트. Grok Bot의 Cursor 번들은 "벤더 번들" 예측의 실현이며, 다중 벤더 조직의 중립 층 수요를 뒷받침한다.

### 11.6 AI 디커플링
- 프론티어 벤더 대비: 자기 에이전트를 자기 도구가 감사하는 구조는 감사인=피감사인이라 조직·규제자가 받아들이지 않는다. 판단·결과 말뭉치는 조직 자산이라 단일 벤더 안에 두지 않는다. 존재 이유는 **벤더 중립 책임 층**. 선례는 OpenTelemetry — 중립 스펙 + 참조 구현. 형식 공개, 필요 시 재단 이관까지 열어 둔다.
- 개인 유입 경로는 벤더가 팀 규칙 동기화·에이전트 거버넌스를 무료로 넣으면 좁아진다 → 매출은 "여러 도구·모델을 쓰며 책임을 증명해야 하는 조직"(감사 가능한 하네스)에서. 개인은 확산용.
- AI 없이도 성립: 닻·해시·원장·범위 해석·자율 수준·결정론적 finding은 AI 무관. AI가 사라지면 "소프트웨어 변경의 책임 원장"으로 남는다(§5 폴백 규칙).
- 통제 불가 변수: 모델이 충분히 좋아져 판단 말뭉치가 정확도에 기여하지 않게 되는 것 — 3개월 실험이 답한다. 그 경우에도 원장·감사 패키지는 남는다.

## 12. 열린 질문
- 하네스 소유자가 하네스를 **이해할 능력**을 어떻게 유지하는가(판단 기록으로 배우는 경로가 부분 답).
- 자율 승격 조건에 규제 요건(범위별 상한)을 1급으로 두는 구체 형식.
- 결과 창 길이와 회귀 정의(소음 설계).
- 도구 훅 지원 범위(구현 직전 확인).
- "의도 없음" 변경의 결정 파생 허용 여부.
- 외부 앵커링의 첫 대상(TSA vs 증인 공동 서명 vs 공개 원장) — 권장 순서 TSA → 증인 → 원장.
- 벤더 서명 영수증(AI 출처 부인 방지) 제공 여부 — 벤더별 확인.
- 감사 패키지의 첫 매핑 대상: SOC2 CC 계열(권장). ISO 27001·AI 규제는 후속.
- 이름. 대외 서사 후보: "AI가 만든 변경을 이해하고 책임질 수 있게" / "당신의 하네스를 소유하라".

## 13. 시나리오

### 13.1 개인 개발자, 첫 주 (팀 없음)
`init`이 기존 규칙 파일 흡수 → 로컬 MCP. 하루 200여 턴의 세션에서 과업 의도 1~2건·작은 요구 10여 건·커밋 수 건이 Change 수 건으로 도출되고, 방향 수정·되돌리기에서 판단 몇 건이 이유와 함께 개인 층에 남는다. 편집 전 훅이 제약에 묶인 닻을 에이전트에게 돌려주는 개입이 하루 한두 번. 사용자가 제품을 "본" 시간 0분. 첫 가치 = 지난 세션의 되돌림 이유를 AI가 읽고 같은 실수를 안 하는 것(닻 이력). 마찰 = 훅 설치, 데이터 불안 → §8 첫 화면 명시.

### 13.2 팀 도입, 4~12주
PR 열 때 세션 사실 공유 선택 → GitHub App 영향 코멘트 → 리뷰어가 세션 판단("캐시 도입 거부, 이유: 정합성")을 봄 → 영향 있는 판단에만 이유 확인 → 같은 닻 3회에 규칙 승격 → 팀 CLAUDE.md managed 블록에 렌더 → 신입이 첫 세션부터 읽음. 마찰 = LGTM 문화 → 이유는 영향 있을 때만, 지표는 "영향 있는 판단의 이유 존재율".

### 13.3 규제 조직, 6~18개월
"AI 생성 코드는 사람 승인 필수" → 제품 층 제약으로 범위 자율 상한 L0 → 분기별 `audit export` → 감사인이 서버 없이 증명 검증. AI 출처 부인 방지 한계는 패키지에 명시. TSA 앵커링 필수화.

### 13.4 비기술 창업가 A (v2, 터미널 없는 경로)
A는 빌더(Lovable·Claude Code 웹 등)로 만든다. 우리는 만들지 않는다. A가 고객이 되는 시점은 **만든 뒤** — 에이전트가 무엇을 깼는지 모르고, 결제 로직을 건드려도 되는지 근거가 없을 때. 경로: GitHub·배포 프로바이더 연결(로컬 설치 없음) → 웹 UI에서 평문 의도 → Work가 클라우드 에이전트에 넘김 → PR → A는 코드가 아니라 평문 영향("결제 계약이 바뀜, ADR-3과 충돌 없음, 24시간 관측")을 보고 클릭 → 배포 → Watch가 회귀 시 되돌림 제안. 자율은 제품 층 기본 상한 L1. 승격 설명 문단은 A 수준으로. 마케팅 등 비코드 산출물은 범위 밖(닻이 없음). 대외 한 줄: "빌더로 만드세요. 운영이 무서워지면 오세요."

### 13.5 자율 확대, 12~24개월
내부 도구의 테스트·문서 범위가 결과 이력으로 L2 승격 제안 → 아키텍트 승인(하네스 변경=L0) → 하네스가 settle, 주간 표본(영향 반경 우선) → 회귀 시 자동 L1 강등 + 예외 → 누락 불변식 승격. 성숙 증거 = 사람 개입당 변경 수 > 10.

### 13.6 기술 흐름과 생존 — 무게 이동
| 흐름 | 반응 |
|---|---|
| 벤더가 거버넌스 번들 (Grok Bot×Cursor로 현실화) | 다중 도구·모델 조직과 규제 축으로. 벤더 규칙 파일을 원본으로 흡수. 승인은 브로커로 통합(중복 승인 금지) |
| AGENTS.md 등 규약 수렴 | 어댑터 감소, 검증·범위·원장에 집중 |
| 에이전트가 클라우드 실행 (Grok Bot·OpenClaw) | 헤드리스 데몬 + 승인 브로커 API(v0) → 원격 MCP(v1). 에이전트 키 관리가 핵심 |
| 모델 품질 급등 | 정확도 도구 → 책임 도구로. 3개월 실험이 전환 시점 표시 |
| 코드 소멸·사용자화 | 지속 객체만 남음. 닻은 `contract://`·데이터·정책으로. §13.7 |
| 규제 착륙 | 감사 패키지·자율 상한·출처 지문이 판매 실체 |

어떤 흐름도 제품을 없애지 않고 무게를 옮긴다(정확도→책임, 코드→제약, 개인→조직, 로컬→클라우드). 각 축의 양쪽을 지원하되 v0는 앞쪽에서 시작한다.

### 13.7 코드 소멸 세계에서의 A
그 세계에서 생성기(빌더)는 범용재가 되고 희소한 것은 하네스(의도·제약·데이터·책임)다. "우리 제품에서 바로 개발"은 우리가 생성기를 만든다는 뜻이 아니라, **의도가 선언되고 제약이 사는 앞면을 우리가 소유하고 실현은 교체 가능한 생성기가 한다**는 뜻이다. 터미널 없는 경로(§13.4)가 곧 그 경로의 초기 형태다. 조건: 하네스가 재생성의 스펙이 될 만큼 완전해야 한다(재생성 가능성). 앞면 소유는 프론티어 벤더와도 경합하므로 중립·책임·데이터 소유가 방어선. 시점: 생성기가 API로 호출 가능해지는 때 — 지금은 만들지 않는다.

### 13.8 팀 B — 개발자 5 · 비개발자 12, AI 중심 6개월 (v1)
상황: 전사 원칙·규제·결정을 git md로 관리했으나, 토론·수정에 git이 필수였고 문서 간 관계가 보이지 않았다. 비개발자가 하네스 소유자보다 많은 첫 사례.
- 이관: 리포 md 일괄 가져오기 → `imported`. AI가 관계·닻 후보 제안, 담당자 확인(2주). 닻 없는 원칙은 "검증 불가"로 정직하게 표시(코드에 닿지 않는 원칙은 `stale` 판정 불가 — 도입 전 고지).
- 이후: 원칙·결정은 원장에 살고 웹·MCP·(원하면) md 렌더로 접근. 12명은 웹에서 토론(Discussion)·수정·하네스 Change 판단, 5명은 에디터·데몬. 비개발자 AI 도구에는 원격 MCP로 검증된 제약 공급. git은 개발자 도구로만 남고 GHA 없이 동작.
- 해소: 관계(그래프·supersedes·what_touches), 충돌(`decision-conflict`), 코드 변경 시 관련 원칙 `stale` → 두 집단이 같은 인박스를 봄.
- 역할: `compliance/*` 하네스 판단자(규제 담당), `product/*` 하네스 판단자(기획), 실현체 판단자(개발자). 첫 달 L0.

### 13.9 기업 C — 세 팀이 한 제품을 분담 (v1)
관심사·원칙·스타일이 팀마다 다르다. 제품 × 팀 격자로: 제품 범위=세 팀 합의 제약(처음엔 거의 비어도 됨, 충돌이 나며 채워짐), 팀 범위=각 팀 원칙·스타일(렌더가 팀별로 다름), 소유 지도=CODEOWNERS 가져오기.
- a팀 개발자가 b팀 소유 닻을 건드림 → 훅이 b팀 제약 주입 → PR 영향 "b팀 제약 2건" → b팀 판단자 없이 settle 불가.
- a팀 "재시도 3회" vs b팀 "재시도 금지"가 같은 계약에 닿음 → `decision-conflict` 제품 인박스 → Discussion → 제품 제약 승격 또는 경계 정리. 지금 C에서는 배포 후에야 드러나는 문제.
- 자율은 팀별(c팀 L2 가능)이되 제품 상한(결제 계약 L0)이 구속.
- 미소유 공유 모듈은 `unowned`로 표시, 제품 판단자 라우팅. 팀 재편 시 소유 지도 이력이 남는 것이 가치.
- UI는 격자를 보여 주지 않고 해석 결과만("이 닻: b팀 소유, 제품 제약 2건 적용").

### 13.10 참고: Foundry의 운영 온톨로지에서 배울 것
- 온톨로지는 문서가 아니라 행동(권한·액션·워크플로)에 결합될 때만 산다 → 우리 규칙 "동작 없는 요소 금지".
- 온톨로지를 팔지 않고 결정과 행동을 판다 → 우리는 하네스·책임을 판다.
- 그들은 포워드 디플로이드로 고객마다 온톨로지를 세운다 → 우리는 그 비용을 못 내므로 코드·커밋·판단에서 **자동으로 채워지는** 온톨로지(닻·소유·충돌·승격)여야 하고, 손으로 세우는 부분은 범위와 소유 지도로 제한.
